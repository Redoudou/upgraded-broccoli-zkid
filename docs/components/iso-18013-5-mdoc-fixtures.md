# ISO 18013-5 mdoc structure and test-credential libraries
_Researched 2026-09-01; independently re-verified 2026-09-02 (see Verification). Every claim carries a source link. Unverified statements are marked [unverified]._

## What it is
ISO/IEC 18013-5:2021 (edition 1, published September 2021, 152 pages, "under review") defines the mobile driving licence as a CBOR document ("mdoc") whose issuer-signed part is `IssuerSigned = { nameSpaces, issuerAuth }` [[2]](#sources) [[1]](#sources). Each data element travels as a tag-24-wrapped `IssuerSignedItem = { digestID, random, elementIdentifier, elementValue }`, and `IssuerAuth` is a `COSE_Sign1` whose payload is the Mobile Security Object (MSO) holding one salted digest per element, the device public key, the docType and a validity window [[1]](#sources). A second edition is a DIS "in the enquiry phase" that adds revocation (status list and identifier list); the EU's tracker records the CD ballot (started 2024-12-11), an expected five-month DIS ballot, and a "Planned publication date: 2026-11-30" (Q4 2026) [[3]](#sources) [[4]](#sources). ISO/IEC TS 18013-7 adds online presentment (first edition TS 18013-7:2024; second edition published as ISO/IEC TS 18013-7:2025, "Edition 2 2025-05", still a Technical Specification, not an International Standard as [[10]](#sources) loosely puts it [[45]](#sources) [[36]](#sources)); the second-edition preview (DTS dated 2025-02-05, marked "FDIS stage") says a "normative Annex C, Digital credentials API retrieval, was added" [[5]](#sources), and AAMVA's July 2026 guidelines describe its three annexes (A REST API, B OpenID4VP draft 18, C DC API) plus a planned Annex D on OpenID4VP 1.0 + HAIP [[7]](#sources). For Green Light the mdoc is the input to the longfellow circuit, and until a DMV partner exists the only mdoc we can prove over is one we issue ourselves with a test IACA and DS certificate (SPEC §6a).

## How Green Light uses it
- **SPEC §2 row "Credential" and §6a.** Real mDLs come from state wallets; the demo runs on "a test mDL signed by our test DMV cert". PLAN M0 ships `scripts/gen-test-dmv.sh`, which today writes an openssl self-signed P-256 cert (no Annex B extensions) and a JSON placeholder; the script's own comment defers "CBOR/MSO encoding of a real mdoc" to M2 "with a proper library". This document picks that library.
- **SPEC §3 circuit statements.** (2) `age_over_21` "salted digest is in the signed MSO" is exactly `valueDigests[ns][digestID] = digest(IssuerSignedItemBytes)` with a ≥16-byte `random` [[1]](#sources); (4) "device-bound key signed the verifier's nonce" is `DeviceAuthentication = ["DeviceAuthentication", SessionTranscript, DocType, DeviceNameSpacesBytes]` signed with the key in the MSO's `deviceKeyInfo` [[1]](#sources) [[20]](#sources). The fixture must therefore be a full `DeviceResponse` (issuer-signed + device-signed) over a SessionTranscript we choose, not just an `IssuerSigned`.
- **PLAN M1/M3/M6.** The bench harness "loads the test mDL from a fixture" (TEST-PLAN group C) and longfellow needs the raw mdoc bytes, the issuer key as `pkx`/`pky` strings, the transcript and `now` [[42]](#sources); longfellow's own embedded test mdocs (26 on `main` today, indices 0–25: Google/Canonical-playground examples, a "Sprind-Funke" mdoc, a Google IACA identity pass, Maryland/Montana/Arizona test and production licences, EU age-verification examples, an Aadhaar example) show the shape the circuit accepts [[43]](#sources). Constraints on our fixture: P-256/ES256 issuer key, SHA-256 digests, MSO ≤ 2551 bytes per the v0.8.6 notes ("~50 attributes"; 2533 bytes of raw MSO once the 18-byte COSE prefix in `mdoc_constants.h` is subtracted), all requested attributes in one namespace [[42]](#sources) [[44]](#sources) [[46]](#sources).
- **PLAN M4 test vectors** (wrong nonce, replayed nonce) need device signatures over arbitrary transcripts: `@owf/mdoc` exposes `SessionTranscript.forIsoMdocDcApi`, `forOid4VpDcApi` and `Holder.createDeviceResponseForDeviceRequest` [[17]](#sources) [[18]](#sources).
- **PLAN M5 / SPEC §4** builds the Merkle tree from VICAL. VICAL aggregates issuing-authority (IACA) public keys [[7]](#sources); the mdoc's `x5chain` carries the DS certificate ("only consists of a single certificate") [[1]](#sources); longfellow's public input is the DS public key [[42]](#sources). The DS-to-IACA link is not in the circuit and not in the trust list. See Status and risks.
- **TEST-PLAN B3, D1, F2, F4** need a second fixture with `age_over_21 = false`, known string values to grep for, and fresh `random` salts per issuance so two proofs are unlinkable.

## How to build or integrate
**Structures to reproduce (DIS 2020 text; the 2021 edition adds `version: "1.0"` and renames `deviceKey` to `deviceKeyInfo`, as every implementation below writes [[20]](#sources) [[39]](#sources) [unverified against the paid text]):**
```
IssuerSignedItem = { "digestID" : uint, "random" : bstr, "elementIdentifier" : tstr, "elementValue" : any }
IssuerSignedItemBytes = #6.24(bstr .cbor IssuerSignedItem)
IssuerAuth = COSE_Sign1   ; payload = MobileSecurityObject; "alg" in protected header;
                          ; DS cert as 'x5chain' (label 33) "as an unprotected header element"
MobileSecurityObject = { "digestAlgorithm" : tstr, "valueDigests" : { "nameSpaces" : { + NameSpace => { + DigestID => Digest } } },
                         "deviceKey" : COSE_Key, "docType" : tstr, "validityInfo" : { signed, validFrom, validUntil, ? expectedUpdate } }
DeviceAuthentication = [ "DeviceAuthentication", SessionTranscript, DocType, DeviceNameSpacesBytes ]
```
Rules from the same text: SHA-256 "recommended"; the digest input "is the binary data of the IssuerSignedItem"; `random` "shall be different for each IssuerSignedItem and shall have a minimum length of 16 bytes"; DigestID "shall be unique within a NameSpace" and "should be dynamic"; `validFrom` not before `issue_date`, `validUntil` not beyond `expiry_date`; ES256/ES384/ES512/EdDSA allowed [[1]](#sources). `age_over_NN` (NN 00–99): a request means "provide the nearest age attestation equal to or larger than NN"; a `false` value "should only be returned if the data item name exactly matches"; values "shall be calculated at the value of the timestamp of the validFrom element" [[1]](#sources). AAMVA 1.6 appends to 7.2.5 that an issuer "shall include in an mDL an age_over_NN statement for each of" its common ages (its example: 18, 21, 65) and recommends attestations for every age in the holder's likely range [[7]](#sources).

**Session transcript for the two DC API paths.** OpenID4VP 1.0 B.2.6.2: `SessionTranscript` per 18013-5 §9.1.5.1 with `DeviceEngagementBytes` and `EReaderKeyBytes` null and `Handover = ["OpenID4VPDCAPIHandover", sha256(cbor([origin, nonce, jwkThumbprint]))]` [[6]](#sources). ISO 18013-7 Annex C (`org-iso-mdoc`), as implemented in `@owf/mdoc`: `["dcapi", SHA-256(CBOR([encInfoB64u, origin]))]` [[19]](#sources) [unverified against the ISO text, which is not in the preview].

**Certificate profiles (Annex B, DIS 2020 tables B.1 and B.3).** IACA: v3, self-signed, `countryName` + `organizationName` mandatory, EC key (P-256/384/521 or Brainpool), Key Usage `keyCertSign` + `cRLSign` (critical), Basic Constraints `CA=TRUE, pathLen=0`, IssuerAltName with `rfc822Name` or `URI`, CRL Distribution Point HTTP URI, validity "Maximum of 15 years" [[1]](#sources). DS: issued by the IACA, "Maximum of 15 months", Key Usage `digitalSignature` only, Extended Key Usage `1.0.18013.5.1.2 (ISO/IEC 18013-5 OID reserved for mDL DS)`, `CA=FALSE`, same IssuerAltName and CRL DP [[1]](#sources). AAMVA 1.6 overrides: `stateOrProvinceName` becomes mandatory in the IACA (and must match `issuing_jurisdiction`), NIST curves only, and IACA validity "Maximum of 20 years" (9 years "sufficient" for mDL-only) [[7]](#sources). Multipaz's `generateIacaCertificate`/`generateDsCertificate` set these extensions (critical Key Usage and Basic Constraints, non-critical IAN and CRL DP); for the DS EKU the code passes `critical = true` to `addExtension` while its own comment says "non-critical", and DIS 2020 Table B.3 marks EKU only "m" (mandatory), not "mc" as it does Key Usage and Basic Constraints [[39]](#sources) [[1]](#sources). Our mapping for `scripts/gen-test-dmv.sh` (openssl x509v3 names, our translation of the tables): IACA `keyUsage=critical,keyCertSign,cRLSign`, `basicConstraints=critical,CA:TRUE,pathlen:0`, `issuerAltName=URI:...`, `crlDistributionPoints=URI:...`; DS `keyUsage=critical,digitalSignature`, `extendedKeyUsage=critical,1.0.18013.5.1.2` (critical follows Multipaz's code, not the DIS table, which does not mark EKU critical), `basicConstraints=critical,CA:FALSE`.

**Recommended for the Node repo: `@owf/mdoc`.** Install `npm i @owf/mdoc` (Node `>=20.19`; deps `@owf/cose`, `@owf/identity-common`, `@owf/token-status-list`, `zod`) [[11]](#sources) [[13]](#sources). Issue (from the project's own DC API fixture) [[21]](#sources):
```ts
const issuer = new Issuer('org.iso.18013.5.1.mDL', mdocContext)
issuer.addIssuerNamespace('org.iso.18013.5.1', { family_name: 'Doe', given_name: 'John', birth_date: '1990-01-01', ...options?.claims })
return await issuer.sign({
  signingKey: CoseKey.fromJwk(ISSUER_PRIVATE_KEY_JWK),
  certificates: [issuerCertificate],            // Uint8Array DER, e.g. new X509Certificate(pem).rawData
  algorithm: SignatureAlgorithm.ES256, digestAlgorithm: 'SHA-256',
  deviceKeyInfo: { deviceKey: DeviceKey.fromJwk(DEVICE_JWK_PUBLIC) },
  validityInfo: { signed, validFrom, validUntil },
})
```
`Issuer.sign(options: { signingKey, algorithm, digestAlgorithm, validityInfo, deviceKeyInfo, certificates: Uint8Array[], status? })` [[15]](#sources); salts are `ctx.crypto.random(32)` and DigestIDs are random, constrained to `[0, 2^31 - 1]` in 0.7.0 [[16]](#sources) [[14]](#sources). Full Annex C round trip, condensed from the project's own test (request → response → verify) [[22]](#sources):
```ts
const { request } = await IsoMdocDcApi.createRequest({ docRequests: [{ docType: mdlDocType, namespaces: { [mdlNamespace]: { family_name: true } } }], recipientPublicKey }, mdocContext)
const parsedRequest = await IsoMdocDcApi.parseRequest({ request, origin }, mdocContext)
const { response } = await IsoMdocDcApi.createResponse({ parsedRequest, documents: [{ issuerSigned, deviceKey, docRequestIndex: 0 }] }, mdocContext)
const { deviceResponse, verificationResult } = await IsoMdocDcApi.verifyResponse({ response, origin, encryptionInfo: request.encryptionInfo, recipientKey: recipientPrivateKey, deviceRequest: DeviceRequest.decode(base64url.decode(request.deviceRequest)), trustedCertificates }, mdocContext)
```
`Verifier.verifyDeviceResponse({ deviceResponse, sessionTranscript, trustedCertificates: [{ issuance: Uint8Array[] }], now?, ... }, ctx)` verifies the result; the `mdocContext` must be supplied by the app — the project's Node test context wires `@peculiar/x509`, `jose`, `@owf/cose`, `node:crypto`, `@noble/curves`, `@panva/hkdf` and `hpke` [[17]](#sources) [[23]](#sources). The test suite (`tests/examples/`) verifies real `DeviceResponse`s from Google Wallet ("Google CM Wallet"), France and Ubique, a BDR `IssuerSigned`, and an `animo-mdoc-05` response against their certificate chains [[11]](#sources) [[24]](#sources).

## Status and risks
- **The standard is moving under us.** Edition 2 is at DIS, planned publication 2026-11-30, adding `status` (ASL/ARL revocation) to the MSO [[3]](#sources) [[4]](#sources). `@owf/mdoc` 0.7.0 already implements "identifier-list revocation (ISO 18013-5 2nd ed § 12.3.6)" and Multipaz tracks the second-edition draft [[14]](#sources) [[36]](#sources). This is the standard answer to SPEC §8 "Revocation … none is ZK-ready"; longfellow's handling of an MSO with `status` is [unverified].
- **We cannot read the normative text.** Structural claims above come from the 2020 DIS plus implementations; the 2020 draft lacks MSO `version`, uses `deviceKey` not `deviceKeyInfo`, and has a two-element SessionTranscript, all of which changed by 2021 per OpenID4VP and every library [[1]](#sources) [[6]](#sources) [[20]](#sources). Buy the 2021 text (and the DIS) before M4 test vectors are frozen.
- **`x5chain` placement disagreement.** DIS: "shall be included as an unprotected header element", single certificate [[1]](#sources). `@owf/mdoc` 0.7.0: "X5Chain is now added to the protectedheaders instead of the unprotectedheaders" and 0.6.0 allows multi-cert chains [[14]](#sources); `pymdoccbor` writes unprotected label 33 [[35]](#sources). Longfellow ignores `x5chain` (issuer key is a public input) [[42]](#sources), so the circuit is unaffected, but any other verifier we test against may reject one or the other.
- **Trust-list gap (SPEC §4, PLAN M5).** VICAL lists IACA keys [[7]](#sources); the presented mdoc carries only the DS certificate [[1]](#sources); the circuit's public input is the DS key [[42]](#sources). Membership of "the issuer cert hash" in a VICAL-derived root therefore needs either DS certificates enumerated in our tree (DS certs rotate within 15 months and are not published in VICAL [[1]](#sources)) or an in-circuit DS→IACA chain check. Neither is in SPEC §6 item 2 today.
- **`@owf/mdoc` maturity.** Pre-1.0, 13 stars, 0.6.0 was a "major library rework" and 0.7.0 changed headers and callbacks [[14]](#sources); pin an exact version and vendor the fixture bytes into `fixtures/` so a library bump cannot silently change M1 numbers. The pluggable context adds roughly six crypto dependencies [[23]](#sources); count them against SIMPLICITY.md.
- **VICAL access is less closed than SPEC §7 says.** The AAMVA RP page describes "free access" at `vical.dts.aamva.org` and the download page lists a current VICAL after accepting the DTS terms [[8]](#sources) [[9]](#sources); the terms themselves were not reviewed [unverified]. PLAN M8 item 4 may be a legal review, not a gated access request.
- **Fixture size.** AAMVA recommends many `age_over_NN` elements per mDL [[7]](#sources); longfellow's MSO cap is 2551 bytes per the release notes (2533 bytes of raw MSO in code) [[44]](#sources) [[46]](#sources). Whether California or New York MSOs fit is [unverified]; keep the test fixture small but also generate one AAMVA-shaped fixture for the M1 benchmark.
- **The MSO hides the DMV, the DS key does not.** Longfellow's `pkx`/`pky` public input identifies the signer; the "issuer list" gadget is not wired (see longfellow-zk.md). Nothing in the credential format helps here.

## Open questions for the partner call
- **AAMVA DTS:** does downloading `vical.dts.aamva.org` for a pilot require registration beyond the click-through terms? Can AAMVA publish DS certificates (or DS key hashes) alongside IACA keys so a trust root can cover what the mdoc actually carries?
- **State DMV (CA / NY):** DS certificate rotation period; MSO byte size and number of `age_over_NN` elements issued; digest algorithm and curve in production (longfellow needs SHA-256 and P-256); is `x5chain` in the protected or unprotected header; is `status` already present in MSOs ahead of edition 2?
- **Google longfellow / Dyne:** will the parser accept an MSO containing the edition-2 `status` element and multi-cert `x5chain`; is an in-circuit DS→IACA check on the roadmap or should Green Light's membership proof be over DS keys?
- **OWF Labs / Animo (`@owf/mdoc`):** timeline to 1.0; rationale for moving `x5chain` into the protected header; would they accept a small "generate test mDL + DeviceResponse" CLI upstream so Green Light does not maintain one?
- **Multipaz / PSE zkID:** can `multipaz-longfellow` prove over an `@owf/mdoc`-issued fixture, giving a second implementation to cross-check M1 numbers?
- **Apple / Google sandboxes:** does the sandbox `DeviceResponse` match the profile above (single DS cert, unprotected header) so one fixture serves both the circuit and the DC API integration tests?
